# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Hakili OCR turns photos/scans/PDFs of administrative documents (tables, forms, records — handwritten or printed) into structured, editable Markdown. A user uploads an image or PDF; the backend sends it to Claude (Anthropic's vision model) with a prompt tuned for administrative table extraction, gets back a list of transcribed "blocks" (each with Markdown text, a bounding box on the source image, and a confidence score), and the frontend renders the source image side-by-side with the transcription, letting the user click a block to highlight its region, edit its text inline, and drag its bounding box if it's misplaced.

**Note (2026-08-24):** the product was repositioned from "handwritten math homework" to "administrative documents structured in tables" — `SYSTEM_PROMPT`/`build_user_prompt` (`claude_service.py`) were rewritten accordingly (all LaTeX/math instructions and the math-vs-administrative disambiguation removed). The JSON/bbox contract (`id`/`label`/`markdown`/`bbox`/`confidence`, `==...==` uncertainty markers, one-block-per-table-row, the color-annotation column) is unchanged — it was already domain-agnostic. Frontend math rendering (KaTeX, `remark-math`, `markdownHighlight.ts`'s math-specific highlighting) was deliberately left untouched: it simply goes unused now rather than being ripped out. Several "math"/"mathématiques" mentions elsewhere in this file (component names, historical rationale) are now about the *previous* domain and were not all swept — treat any remaining math-specific framing below as historical unless a section says otherwise.

## Repository layout

This repo contains two independent projects (no shared tooling or monorepo config for local dev), plus a root-level Docker Compose setup that runs both together:

- `ocr-math-api/` — Python/FastAPI backend that calls the Claude (Anthropic) API to OCR handwritten math homework into structured LaTeX/Markdown. Own `Dockerfile`/`.dockerignore`.
- `hakili-ocr/` — React 19 + TypeScript + Vite frontend that uploads images/PDFs to the backend and renders the results with an editable, block-by-block viewer. Own `Dockerfile`/`.dockerignore` (multi-stage build → static files served by nginx, `nginx.conf`).
- `docker-compose.yml` (repo root) — builds and runs both services together; see "Docker / deployment" below.
- `.env` / `.env.example` (repo root) — variables consumed by `docker-compose.yml` itself (distinct from each project's own `.env`/`.env.example`, which are for running that project outside Docker).

They communicate only over HTTP: the frontend calls the backend at `VITE_API_BASE_URL` (`hakili-ocr/src/services/apiClient.ts`, falls back to `http://127.0.0.1:8000` if unset), and the backend's CORS middleware in `ocr-math-api/app/main.py` allows the origins listed in `ALLOWED_ORIGINS` (`app/config.py`, defaults to `http://localhost:5173,http://localhost:5174,http://localhost:8021` — Vite's dev ports plus the dockerized frontend's host port). Both must be running for the app to work end to end, whether started locally or via Docker Compose.

## Backend architecture (`ocr-math-api/`)

### Image transcription (`POST /transcribe`)

Defined in `app/routers/transcription.py`:

1. **Validate** content type (`app/utils/image_utils.py`: `validate_content_type`) and stream-read the upload with a size cap (`read_upload_with_limit`/`read_upload_with_byte_limit`, which abort with a `ValueError` as soon as the budget is exceeded rather than buffering the whole body first — there is no separate `validate_size` function).
2. **Normalize** EXIF orientation (`normalize_orientation`) and **resize** the image to fit Claude's vision limits — max edge 1568px, max ~1568 vision tokens computed via a 28px tiling formula (`resize_for_vision` / `resized_size`).
3. **Call Claude** (`app/services/claude_service.py`, `call_anthropic_ocr`, `async`): sends the base64 image plus a French system prompt (`SYSTEM_PROMPT`, rewritten 2026-08-24 to focus solely on administrative documents — see note under "What this project is" above) instructing the model to:
   - ignore crossed-out/scribbled content and transcribe only the final clean content,
   - wrap any content it isn't confident it read correctly — even a single digit, letter, or symbol — in `==...==` highlight markers (unrelated to the strike-out rule: highlighting means "uncertain," not "crossed out"),
   - for tables, emit **one block per data row** rather than one block for the whole table: each row-block repeats the header + separator line followed by just that row's data, with its own `id`/`label`/`bbox`/`confidence`,
   - if a cell has extra handwriting in a visibly different color (often red vs. black/blue original text) layered on top of the original text, add a dedicated "Annotation" column to that table and keep the original cell text clean — this is neither an uncertainty nor a strike-out, both are legible and must be kept separate (this rule used to be scoped to "administrative/accounting tables only, never math" — now unconditional, since every document is administrative),
   - return bounding boxes in **absolute pixel coordinates** (the exact resized image dimensions are given to the model in the user message — the model must not estimate fractions itself).

   `SYSTEM_PROMPT` is sent with Anthropic prompt caching enabled (`cache_control: {"type": "ephemeral"}` on the system block, added 2026-08-24) — it's identical across every call, so once a job's first call writes the cache, subsequent calls within the 5-minute TTL (kept warm by the steady call rate under `ANTHROPIC_CONCURRENCY`) pay ~90% less for that portion and get a faster response (no reprocessing of that prefix). Purely additive: no behavior change, only cost/latency.
4. If `message.stop_reason == "max_tokens"`, the response is treated as a truncation error (raises `ValueError`) rather than being force-parsed as JSON — a longer/more verbose response (e.g. pages with tables) can exceed `MAX_TOKENS` and get cut off mid-JSON.
5. **Parse and normalize the response** (`parse_claude_response`): strips optional ```` ```json ```` fences, parses JSON, silently drops any table-row block Claude generated with no actual data (`_is_blank_table_row_block` — header+separator present but the data line is empty once `|` characters are stripped), converts each remaining block's pixel bbox into a 0–1 normalized fraction using the same width/height that was sent to Claude, injects a "Confiance" column into every table-row block's markdown (`inject_confidence_column`, keyed off that block's own `confidence` field — the single source of truth, so Claude is never trusted to retranscribe the percentage itself, keeping it consistent with the bbox color shown on the frontend), and validates the result against the `OCRResult` Pydantic schema (`app/models/schemas.py`).
6. Bounding boxes are clamped to `[0, 1]` and `x_max`/`y_max` are validated to be ≥ their `_min` counterpart via Pydantic field validators on `BoundingBox`.

`describe_anthropic_error` (`claude_service.py`, extended 2026-08-24) classifies Anthropic errors by type/`status_code` into a French, actionable message instead of leaking the raw API error JSON to the end user — covers credit balance too low (400 + specific text), auth (401), permission (403), rate limit (429), server overload/5xx (`InternalServerError`/`OverloadedError`), connection/timeout (`APIConnectionError`), request too large (413), and a generic bad-request fallback; anything else falls back to `str(exc)`. This is the single place both `transcribe_image` (image flow) and `_process_page_and_track` (PDF page flow) translate an `anthropic.APIError` into the message shown to the user, so extending it here covers both flows. `_process_page_and_track`'s catch-all `except Exception` branch (non-Anthropic failures) was also changed to include the real exception detail in the page's warning shown to the user, not just a generic "échec de la transcription" — avoids a silent-looking failure for unexpected errors.

Key architectural point: bbox normalization always divides by the dimensions of the *resized* image actually sent to Claude, not the original upload — this consistency is what keeps frontend-rendered boxes aligned with the displayed (resized) image.

The Anthropic client is `anthropic.AsyncAnthropic`, built once via a module-level `@lru_cache`d `_get_client()` in `claude_service.py` and reused across calls (HTTP keep-alive, no per-call reconnect). `call_anthropic_ocr` is `async` and does `await client.messages.create(...)` — this matters because the route handlers are `async def`; a blocking/sync Anthropic call there would stall the whole event loop, not just the current request. The actual network call is wrapped in a **global** `asyncio.Semaphore` (`_get_semaphore()`, also `@lru_cache`d — created lazily rather than at module import time, so it binds to the event loop that's actually running when first used), sized by `ANTHROPIC_CONCURRENCY` (default `6`): bounds how many Anthropic calls are ever in flight at once, whether they come from one PDF job's parallel pages or from multiple jobs/users at the same time — protects against Anthropic rate limits (429s) and uncontrolled cost/load spikes.

**Retry/backoff and timeout (added 2026-08-24):** `_get_client()` sets `max_retries=0` (disables the SDK's built-in retry) and an explicit `timeout=ANTHROPIC_REQUEST_TIMEOUT_SECONDS` (default 120s, `config.py`). Retries are instead handled by `_create_message_with_retry` (`claude_service.py`), which retries only transient errors (`_is_retryable_anthropic_error`: 429, any 5xx, or a connection/timeout error) up to `ANTHROPIC_MAX_RETRIES` additional attempts (default 3), with exponential backoff + random jitter (`ANTHROPIC_RETRY_BASE_DELAY_SECONDS`, default 1s) between attempts. The key design point: the semaphore (`async with _get_semaphore():`) is only held during the actual network call, re-acquired fresh on each attempt — the `asyncio.sleep` backoff between attempts happens *outside* it, so a page waiting to retry after a 429 doesn't monopolize one of the 6 concurrency slots while it waits (unlike the SDK's own retry, which would keep the slot held for the whole retry+backoff duration since it all happens inside one `await client.messages.create(...)`). Non-retryable errors (400/401/403/404/422...) and exhausted retries are re-raised as the original exception type unchanged, so `describe_anthropic_error`/the callers' `except anthropic.APIError` handling needed no changes.

### PDF transcription (`POST /transcribe/pdf/start` + `GET /transcribe/pdf/status/{job_id}`)

PDFs are **not** processed synchronously within one HTTP request — a long PDF (dozens/hundreds of pages) would otherwise mean one very long blocking POST. Instead:

1. `POST /transcribe/pdf/start` validates the upload, rasterizes every page to PNG via PyMuPDF (`convert_pdf_to_images`, 150 DPI), creates a job (`app/services/job_store.py`, in-memory `dict[job_id -> PDFJob]`), and schedules `_run_pdf_job(job_id, page_images)` as a **fire-and-forget** `asyncio.create_task` — the endpoint returns `{ job_id, pages_total }` immediately, before any page is transcribed.
2. `_run_pdf_job` processes all pages **in parallel** via `asyncio.gather` over `_process_page_and_track` (one task per page) — actual Anthropic concurrency stays bounded by the global semaphore above (`ANTHROPIC_CONCURRENCY`), not by this loop. Each task writes its `PageResult` into `job.results: dict[int, PageResult]` keyed by `page_number` (a shared field on the job itself, not a dict local to this call — since 2026-08-21, so that `GET /pdf/status` can read it mid-flight for progressive display, same field the chunked flow below already used) since tasks finish in an arbitrary order under concurrency; `_finalize_pdf_job`/`_build_pdf_result` (shared with the chunked flow below) sort `results.values()` by `page_number` so the final result stays in document order. Each task also increments `job.pages_done` itself, as a side effect right before it returns — this makes progress visible to the status endpoint in real time as pages complete, without waiting for `gather` (which only unblocks its caller, `_run_pdf_job`, once *every* task is done) to return. Per-page failures (`anthropic.APIError` or any other exception) are caught inside each task, same as before parallelization — one page failing never cancels the others; warnings/errors are collected as `(page_number, message)` pairs and sorted by page number before being joined, for a deterministic `final_warning`/`job.error` regardless of completion order.
3. `GET /transcribe/pdf/status/{job_id}` returns the job's current `status` (`"processing" | "done" | "error"`), `pages_done`/`pages_total`, and `result`. Since 2026-08-21 (progressive page display, see below), `result` is populated as soon as at least one page is ready — not only once `status == "done"` — built on the fly from `job.results` via `_build_pdf_result` (shared with `_finalize_pdf_job`). The frontend polls this endpoint (every 8s, `PDF_POLL_INTERVAL_MS` in `useTranscribe.ts`) both to show real per-page progress and to progressively reveal pages, instead of waiting for the whole document. Reused unchanged by the chunked flow below — it has no idea whether a job was created by `/pdf/start` or `/pdf/start-chunked`.

**Known limitation**: `job_store.py`'s job dict is process-local memory — jobs are lost on restart and it wouldn't work across multiple workers/processes (would need Redis or similar for that). The app is built as a **multi-user SaaS**, not a personal-use tool — this is an accepted limitation only as long as the deployment stays pinned to a single, vertically-scaled instance (see "Production readiness" below), not a long-term assumption.

Config (`app/config.py`) is loaded once via `@lru_cache` from environment variables (`.env` via `python-dotenv`): `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` (default `claude-sonnet-5`), `MAX_IMAGE_SIZE_MB` (default `5`), `MAX_PDF_SIZE_MB` (default `500`), `MAX_PDF_PAGES` (default `600`), `JOB_TTL_SECONDS` (default `14400`, 4h), `ANTHROPIC_CONCURRENCY` (default `6`), `JOB_STALL_TIMEOUT_SECONDS` (default `1800`, 30 min — see chunked upload below), `MAX_TOKENS` (default `8192`, code and `.env.example` aligned since 2026-08-24 — previously the code default was `4096`), `ANTHROPIC_REQUEST_TIMEOUT_SECONDS` (default `120`), `ANTHROPIC_MAX_RETRIES` (default `3`), `ANTHROPIC_RETRY_BASE_DELAY_SECONDS` (default `1`) — the last three added 2026-08-24, see "Retry/backoff and timeout" above.

Error handling convention in the router: `ValueError` → 400/422 depending on stage, `RuntimeError` (missing API key) → 500, `anthropic.APIError` → 502, anything else → 500. PDF uploads are validated against `MAX_PDF_SIZE_MB` (a dedicated limit, no longer derived from the image limit) and `MAX_PDF_PAGES` (rejected with 400 before any page is rasterized) — matches the frontend's client-side check in `UploadScreen.tsx` (5 MB for images, 500 MB for PDFs).

#### Chunked PDF upload (`POST /transcribe/pdf/start-chunked` + `POST /transcribe/pdf/{job_id}/chunk`, implemented 2026-08-20)

An **additional** path alongside `/pdf/start` above (which stays completely unchanged) for large PDFs: instead of one blocking upload of the whole file followed by processing, the client splits the PDF into sub-PDFs client-side (`hakili-ocr/src/utils/pdfChunking.ts`, `loadPdf` + `splitLoadedPdfIntoChunks` — pure `pdf-lib` page copying via `PDFDocument.create()`/`copyPages`/`addPage`, **no pixel rendering**; PyMuPDF stays the sole rasterizer, unchanged) and sends them one at a time, **strictly sequentially** (chunk N+1 is only sent after chunk N's response is received — no client-declared page ordering is needed, since the backend numbers pages itself via a running `pages_received` counter). This overlaps the two phases that used to be sequential: the backend starts transcribing chunk N's pages in the background while chunk N+1 is still uploading, so total wall-clock time trends toward `max(upload time, processing time)` instead of their sum. Used only above `PDF_CHUNK_PAGE_COUNT_THRESHOLD` pages (`pdfChunking.ts`, default `30`) — smaller PDFs keep the plain `/pdf/start` flow, since chunking a small file adds round-trips for no benefit. Chunk size defaults to `PDF_CHUNK_SIZE_PAGES = 20` (comfortably above `ANTHROPIC_CONCURRENCY = 6` so one chunk keeps the semaphore saturated while the next uploads).

- `PDFJob` (`job_store.py`) gained chunked-only fields, left at their defaults by a legacy `/pdf/start` job: `pages_expected` (client-announced page count, clamped server-side to `MAX_PDF_PAGES` by `create_chunked_job` — doubles as the legacy/chunked discriminant, `None` for legacy jobs), `pages_received`/`bytes_received` (server-computed running totals, never trusted from the client), `chunks_pending` (task groups currently processing a chunk), `upload_finalized` (set once the chunk marked `is_last_chunk=True` is accepted), `updated_at`, and `results`/`warnings`/`errors` (the same containers `_run_pdf_job` uses as locals, promoted to job fields here since a chunked job accumulates them across multiple separate requests over time, not one function call) plus a per-job `asyncio.Lock`.
- `POST /pdf/start-chunked` takes just `{ pages_expected }` (no file yet) and returns `{ job_id, pages_total }`, reusing `PDFJobStartResponse` as-is.
- `POST /pdf/{job_id}/chunk` (multipart: `file` + `is_last_chunk`) rejects with 404 (unknown job), 409 (the job wasn't opened via `/pdf/start-chunked` in the first place — `pages_expected is None` means it's a legacy job; job already done/error/finalized; or another chunk for this job is still being read — `job.lock` fails fast rather than queuing silently, since two overlapping chunk requests mean the client broke the sequential-sending contract), or 400 (non-PDF content, or the chunk would exceed the job's *remaining* byte/page budget — `read_upload_with_byte_limit`/`count_pdf_pages` are called with `remaining_bytes`/`remaining_pages` derived from the job's running totals, not the raw `MAX_PDF_SIZE_MB`/`MAX_PDF_PAGES` constants, which is what makes the existing per-call checks enforce a cumulative ceiling across however many small chunks a client spreads pages over). On success it schedules `_process_chunk_pages` (same `_process_page_and_track` fan-out as `_run_pdf_job`, but writing into `job.results`/`job.warnings`/`job.errors`) as a background task and returns `PDFChunkAckResponse { job_id, pages_received, status }`.

  **Rasterization deferred to the background task (changed 2026-08-24):** `upload_pdf_chunk` used to call `convert_pdf_to_images` (the actual PyMuPDF pixel rendering) itself, under `job.lock`, before responding — but since the client only sends chunk N+1 after receiving chunk N's HTTP response (strictly sequential contract), that render time was never overlapped with anything and added pure latency (tens of seconds cumulated over ~25 chunks for a 500-page document). Now `upload_pdf_chunk` only calls `count_pdf_pages` (`image_utils.py`, added 2026-08-24 — opens the PDF just to read its page count for budget validation, no pixel rendering, far cheaper than `convert_pdf_to_images`) under the lock, then responds immediately; `_process_chunk_pages` does the actual `convert_pdf_to_images` rasterization itself, in the background, right before OCR — so it now overlaps with the next chunk's upload, like the OCR step already did. `job.lock`'s scope shrank accordingly (byte-read + cheap page count only, not rasterization). Trade-off accepted: a chunk whose rasterization fails (rare — most corrupt-PDF cases are already caught by `count_pdf_pages`'s `fitz.open()`) no longer surfaces as an HTTP 400 on the chunk POST; instead all pages in that chunk are marked failed via `job.warnings`/`job.errors` (same per-page-failure shape as an OCR failure), visible only on the next `/pdf/status` poll — and since a single `convert_pdf_to_images` call covers the whole chunk, per-page failure granularity is lost in this specific case (one bad page fails its whole chunk, not just itself).
- Job completion isn't a single `gather` anyone awaits: `_maybe_finalize_job` runs at the end of *every* chunk's processing (not just the chunk sent last — the chunk that finishes processing last in real time isn't necessarily the one uploaded last) and finalizes once `chunks_pending == 0 && upload_finalized` — both conditions checked with no `await` in between, so it's race-free under asyncio's single event loop without needing a lock here.
- `image_utils.py`'s `read_upload_with_limit` (single-shot, Mb-based budget) is now a thin wrapper over `read_upload_with_byte_limit` (byte-based, reusable with a *shrinking* budget across multiple requests) — behavior for existing callers (`/transcribe`, `/pdf/start`, `/corrections`) is unchanged.
- `_purge_expired_jobs` (`job_store.py`) now also sweeps chunked jobs stuck mid-upload (`upload_finalized=False`, `status == "processing"`) whose `updated_at` is older than `JOB_STALL_TIMEOUT_SECONDS` — without this, a client that abandons an upload part-way (closed tab, dropped connection) would leave a `"processing"` job in memory forever, since nothing else would ever flip its status away from `"processing"`.
- Frontend: `useTranscribe.ts`'s `start(file)` calls `loadPdf(file)` (`pdf-lib`, no rasterization) once to get both the page count *and* a loaded `PDFDocument`, to decide `/pdf/start` vs. the chunked path; the chunked path (`startPdfChunkedFlow`) opens the job, then reuses that same already-loaded `doc` in `splitLoadedPdfIntoChunks` (rather than re-reading/re-parsing `file` a second time — `loadPdf` and `splitLoadedPdfIntoChunks` were originally two independent functions that each called `PDFDocument.load` on the same file; merged 2026-08-20 once this redundant double-parse was identified as wasteful for large PDFs), then `for`-loops `await uploadPdfChunk(...)` per chunk. Once `pdfJobId` is set (right after the job opens, before any chunk is sent), the **existing** `statusQuery` polling takes over unchanged — `progress`/`data` already reflect real accumulating progress while the chunk-sending loop is still running, no new UI plumbing needed. Two additive-only pieces of state (`isChunkedStarting`, `chunkUploadError`) fold into the *existing* `isPending`/`isError`/`error` fields of `UseTranscriptionResult` — the hook's returned shape is unchanged, so `LoadingScreen`/`ResultScreen` needed zero modifications.
- **Known remaining inefficiency, not yet addressed**: `PreviewScreen.tsx`'s `usePdfPreview` (eagerly renders *every* page as a full PNG data URL, only committing state once the entire loop finishes) and `fileTransform.ts`'s `rotatePdfFile` (full `PDFDocument.load`+`save()`, only when a page was actually rotated) each independently parse/render the same document again, before `loadPdf` above ever runs — for a 600-page PDF this means the file's content is walked multiple times across the upload flow (preview rendering, optional rotation, page-count+chunking), none of it in a Web Worker. Flagged 2026-08-20, intentionally not fixed yet — pending a product decision on a shared "large document" page-count threshold across preview/rotation/chunking before choosing an approach (lazy per-page preview rendering being the leading candidate).
- Verified 2026-08-20 with real Claude calls (not just mocked orchestration tests): a 3-page document sent as two chunks (2 pages + 1 page) produced a `PDFTranscriptionResult` structurally identical (same keys, same page order, same per-page shape) to the same document sent whole via `/pdf/start`.

#### Progressive page display (implemented 2026-08-21)

Instead of waiting for the entire PDF to finish before showing anything, the frontend now displays and lets the user review/edit already-transcribed pages while the rest keep processing in the background — requested so a long document doesn't feel like dead time.

- **Backend**: no new endpoint — `GET /pdf/status/{job_id}` (see point 3 above) now returns a partial `result` while `status == "processing"`, built by `_build_pdf_result` from whatever's in `job.results` so far. This required `_run_pdf_job` (legacy flow) to start writing into the job's own `results`/`warnings`/`errors` fields instead of locals to the function call — the chunked flow already did this, so both flows now expose partial results identically.
- **Frontend** (`useTranscribe.ts`): `takeReadyPagePrefix` only reveals the **contiguous prefix starting at page 1** while `status === "processing"` — pages complete in an arbitrary order under concurrency (`ANTHROPIC_CONCURRENCY`), so `job.results` can already have page 5 without page 3; showing that as-is would make the array index used everywhere on the frontend (`ResultScreen`, `AppContext`) stop matching `page_number - 1`, and an already-displayed page could "shift" to different content on the next poll. Once `status !== "processing"`, no more filtering — a remaining gap at that point is a page that failed for good, not one still in flight.
- **`AppContext.tsx`**: `SET_RESULT` still handles the very first reveal (switches to the `'result'` screen, resets navigation). A new `MERGE_PDF_RESULT` action handles every later poll — it appends newly-ready pages to the already-displayed `pdfResult` without resetting `currentPageIndex`/`selectedBlockId` or touching pages the user is currently viewing/editing. Safe by construction: a page's content never changes once transcribed, so a longer incoming `pages` array is always a strict extension of what's already shown, never a conflicting rewrite.
- **`AppState.pdfPagesTotal`**: the document's true total page count (known from the very first status poll via `progress.pagesTotal`), tracked separately from `pdfResult.pages.length` (which only reflects pages loaded/revealed so far). `ResultScreen.tsx` uses this split as `pagesLoaded` (bounds the "next page" button) vs `totalPages` (what the header actually displays, e.g. "3 / 40" even while only 3 are in).
- **`ResultHeader.tsx`**: "next page" is disabled beyond `pagesLoaded` (blocks navigating into a page not transcribed yet, rather than showing a placeholder); a small pulsing "Transcription en cours…" indicator shows next to the page counter while `isStreaming`; the Excel/PDF export buttons are disabled while streaming, to avoid silently exporting an incomplete document.
- **Known limitation**: if page 1 fails permanently while later pages succeed, nothing is shown until the job fully finishes — `takeReadyPagePrefix` never reveals anything without page 1 present. Accepted trade-off (page-level failures are rare), not fixed.

### Corrections dataset (`POST /corrections`)

When a user fixes a block's transcribed text in the frontend, the app can optionally capture that correction for future prompt/model improvement: the cropped source-image region for that block, the original (Claude-transcribed) text, the corrected text, and a free-text description of what was wrong.

- Storage is SQLite (stdlib `sqlite3`, no new dependency) plus PNG files on disk, under `ocr-math-api/data/` (gitignored, path anchored on `__file__` so it doesn't depend on the cwd `uvicorn` is launched from) — consistent with the same single-process assumption as `job_store.py`, accepted for now only as long as the deployment stays pinned to one instance (see "Production readiness" below), not a long-term assumption given the app is a multi-user SaaS.
- `app/services/correction_store.py` owns the schema (`corrections` table: id, image_path, block_label, confidence, original_markdown, corrected_markdown, error_description, created_at) and `save_correction(...)`, which writes the image then the row in one transaction. `sqlite3.Connection` isn't thread-safe, so each call opens/closes its own connection rather than sharing one — the endpoint invokes it via `asyncio.to_thread`, potentially from a different thread each time.
- `app/routers/corrections.py` exposes `POST /corrections` as multipart (`image` file + form fields), reusing `validate_content_type`/`read_upload_with_limit` from `image_utils.py` (the latter streams the upload in chunks and aborts as soon as it exceeds `MAX_IMAGE_SIZE_MB`, rather than buffering the full body before checking) and rejecting an empty error description.

### PDF export (`POST /export/pdf`)

Lets the user download the transcription as a real vector PDF (selectable text, not a rasterized screenshot) — a deliberate second-generation approach replacing an earlier `html2canvas` + `jsPDF` attempt (rasterized, no selectable text).

1. The frontend renders the transcription off-screen with `TranscriptExport.tsx` (React + KaTeX, a template dedicated to export — no Tailwind classes, no edit controls, no per-cell memoization) into a detached DOM node, waits two `requestAnimationFrame`s for KaTeX to paint, then serializes `.innerHTML` (`hakili-ocr/src/utils/exportPdf.tsx`, `exportTranscriptionToPdf`). Uncertain-content `==...==` markers are stripped first via `utils/exportSanitize.ts`'s `sanitizeExportPages` (shared with the Excel export below) — they only make sense in the interactive UI.
2. That HTML fragment is POSTed as JSON (`{ html }`) to `POST /export/pdf` (`app/routers/export.py`).
3. `app/services/pdf_export_service.py`'s `render_export_pdf` wraps the fragment in a full HTML document with a dedicated print stylesheet (`@page` size/margins, all-black text, table rows that avoid breaking across pages, cells that wrap instead of truncating) plus the local KaTeX stylesheet (`app/static/katex/katex.min.css`), then calls **WeasyPrint** (`HTML(string=...).write_pdf()`) — no headless browser, no JS execution needed since KaTeX already produced static HTML/CSS client-side.
4. `weasyprint` is imported lazily inside `render_export_pdf` (not at module top-level): on Windows it requires the native GTK3/Pango runtime to be installed separately, and a top-level import would crash the whole API's startup — including endpoints unrelated to export — the moment that runtime is missing. The Docker image installs the required libraries (`libpango-1.0-0`, `libpangoft2-1.0-0`, `fonts-dejavu-core`) so export works out of the box there regardless of the host OS.
5. `export_pdf` runs `render_export_pdf` via `asyncio.to_thread` (WeasyPrint's layout/rasterization is CPU-bound/blocking), same pattern as `correction_store.save_correction` and the transcription pipeline.

A sibling **Excel export** (`.xlsx`) is entirely client-side, no backend involvement — see `utils/exportExcel.ts` under Frontend architecture below.

## Frontend architecture (`hakili-ocr/`)

Single-page app with four screens (`upload` / `preview` / `loading` / `result`) driven by one `useReducer`-based context, no router:

- `src/context/AppContext.tsx` — global state (`AppState`) and all transitions (`AppAction`). `SET_IMAGE` (file picked) moves to `'preview'`, not straight to `'loading'`; `CONFIRM_UPLOAD` (user clicks "Envoyer" in the preview screen) moves to `'loading'` with the possibly-transformed file; `CANCEL_PREVIEW` goes back to `'upload'`. `UPDATE_BLOCK_MARKDOWN` and `UPDATE_BLOCK_BBOX` update a single block's text or bbox in place (for both the plain-image result and, if a PDF is loaded, the current page inside `pdfResult.pages`) without reparsing the whole transcription result. For a PDF, `SET_RESULT` only fires the first reveal (switches to `'result'`); every later poll goes through `MERGE_PDF_RESULT` instead, and `pdfPagesTotal` tracks the document's true page count separately from how many pages are loaded so far — see "Progressive page display" under Backend architecture above.
- `src/components/PreviewScreen.tsx` — shown between upload and loading. Lets the user rotate the document (90° steps) before sending, tracked as `Record<pageIndex, RotationAngle>` local `useState` (so a multi-page PDF can have a different rotation per page, not just one global angle) — not global app state. A `rotationScope` toggle ("Cette page" / "Toutes les pages") lets the user apply one rotation to every page at once instead of picking each page individually. For PDFs, renders a client-side page-by-page preview via `src/hooks/usePdfPreview.ts` (`pdfjs-dist`, its Web Worker entry point `src/hooks/pdfWorkerEntry.ts` installs a `Promise.withResolvers` polyfill before `pdfjs-dist` needs it — must run first in the worker's scope, see the detailed comment there for the compatibility bug it works around), with prev/next navigation between pages. On confirm, `src/utils/fileTransform.ts`'s `applyRotation` applies the rotation(s) to the *actual file* before it's sent — canvas redraw for images (`rotateImageFile`, single angle), PDF `/Rotate` page metadata per page via `pdf-lib` for PDFs (`rotatePdfFile`, the whole rotations map — respected by PyMuPDF server-side, so it doesn't need to re-rasterize the visual preview). If no page was rotated, the original `File` is sent unmodified.
- `src/hooks/useTranscribe.ts` — exports `useTranscription()`, the single entry point used by `App.tsx` to kick off and track a transcription, for either file type:

Both paths are normalized into one return shape: `{ start, isPending, isError, error, progress, data }`, where `progress` (`{ pagesDone, pagesTotal }`) is only non-null for the PDF/job path.
  - Has a `USE_MOCK` flag (currently `false`) that bypasses the network entirely with hardcoded `MOCK_RESULT`/`MOCK_PDF_RESULT` fixtures, for frontend-only development.
  - Normalizes `final_warning: null` (from the backend) to `undefined` for consistent optional-field handling in TS. Throws typed `TranscribeError` with `statusCode`/`isRetryable` based on backend HTTP status, built on the shared `apiClient.ts`.
- `src/services/apiClient.ts` — shared `API_BASE`/`TranscribeError`/`fetchApi` used by both `useTranscribe.ts` and `correctionsApi.ts`.
- `src/components/LoadingScreen.tsx` — always shows a generic indeterminate spinner + cycling status-text animation + sweeping progress bar, for both images and PDFs (simplified 2026-08-24: the earlier dual-mode behavior — a real "Page X / Y" counter and proportional bar when a PDF's `progress` was available — was removed; the component no longer takes a `progress` prop at all). Deliberate: no page count is shown before the first page is ready. `App.tsx` still switches to `'result'` (`SET_RESULT`) as soon as page 1 arrives, unchanged — from then on, `ResultHeader`'s own "Transcription en cours…" indicator (fed by `progress`, still passed to `ResultScreen`) covers progress on later pages.
- `src/components/UploadScreen.tsx` — drag-and-drop / file-picker entry point; client-side validates file type (PNG/JPEG/PDF) and size (5 MB images, 500 MB PDFs) before dispatching `SET_IMAGE`, mirroring the backend's own limits (page-count is only enforced server-side, once the file is uploaded).
- `src/components/ResultScreen.tsx` — renders the source image with overlaid, color-coded (by confidence) bounding boxes alongside Markdown+LaTeX block content, supports selecting a block to scroll/highlight, and PDF page navigation (`pdfResult.pages`, `currentPageIndex`). Takes an optional `progress` prop (threaded from `App.tsx`) used only to derive `isStreaming` (still more pages coming) for `ResultHeader`; distinguishes `pagesLoaded` (`pdfResult.pages.length`, bounds the "next page" button) from `totalPages` (`pdfPagesTotal ?? pagesLoaded`, what the header displays) — see "Progressive page display" above.   - `src/hooks/useRowSelection.ts` — `handleRowClick`/`cancelPendingRowClick`, including the 300ms debounce described below.
  - `src/hooks/useCorrectionCapture.ts` — `pendingCorrection`/`isSubmittingCorrection`, `captureCorrection`/`handleCancelCorrection`/`handleSubmitCorrection` (crops the image, opens/submits `CorrectionModal`).
  - `src/components/result/AnnotatedImagePanel.tsx` — the image column: source image with overlaid `BlockOverlay` boxes.

  - `src/utils/tableMarkdown.ts` — table markdown parsing: `tableLines`, `parseTableRowCells`, `withReplacedCell`, `getRowCellTexts`, `isTableBlockMarkdown`, `groupBlocksForRender`/`RenderGroup`, `insertPageAndRowColumns` (inserts "Page"/"Ligne" columns after "Confiance" — used by the in-app table rendering below and by both export paths, so exported files can be traced back to their source page/row). `parseTableRowCells` splits a row on `|` but is aware of `$...$`/`$$...$$` spans (and `\|`), so a literal `|` inside math (`$P(A|B)$`, `$|x|$`) doesn't get misparsed into two malformed cells.

  - `src/utils/geometry.ts` — pure functions for bbox math: `pixelDeltaToNormalized` (screen-pixel delta → `[0,1]` fraction, scaled to the container that bbox `%`s are relative to) and `translateBBox` (translate a bbox keeping width/height fixed, clamped per-axis so it stops at the image edge rather than being truncated).

A distance threshold (`DRAG_THRESHOLD_PX = 4`) distinguishes a click (fires the existing selection `onClick`) from a drag (fires `onDragEnd` with the final bbox). High-frequency drag state stays in refs/local hook state; only one `dispatch(UPDATE_BLOCK_BBOX)` fires, on release.
  - `src/components/result/dragContext.ts` — `DraggingBlockContext` (which block is being dragged, changes rarely) and `DragOffsetContext` (the live pointer delta, changes on every `pointermove`), split so a `pointermove` doesn't re-render every other box on the image.

Memoized, keyed on `block.id`, subscribes only to `DraggingBlockContext`; only the actively-dragged box mounts the inner `DraggingBlockBox`, which reads `DragOffsetContext` and computes its live position via `translateBBox`. Uses an inline SVG cursor (black hand, white outline) instead of the native `grab`/`grabbing` cursor, which renders illegibly white on this panel's light boxes.

Deliberately a separate template from `ContentPanel`/`TableRow` (no edit controls, no per-cell memoization, no Tailwind classes) since the serialized HTML ships without its stylesheet — only the backend's export template CSS (`h2`/`table`/`th`/`td` selectors, `.block`/`.table-wrap` classes) applies once it reaches WeasyPrint.
  - `src/utils/exportExcel.ts` — `exportTranscriptionToExcel(pages, filename)`: builds an `.xlsx` workbook client-side (`xlsx`/SheetJS, dynamically `import()`-ed so it doesn't bloat the main bundle for users who never export), one sheet per source page. Table-row block groups become real Excel tables (header + one row per block, via `getRowCellTexts`, with "Page"/"Ligne" columns from `insertPageAndRowColumns`); Markdown/LaTeX is written as raw source text (Excel can't render formulas, so `$x^2$` stays literally `$x^2$`). No backend involvement at all.
  - `src/utils/exportSanitize.ts` — `sanitizeExportPages`, shared by both export paths: strips `==...==` uncertain-content markers from every block before export, since they only mean something in the interactive UI (`<mark>`/`\colorbox`), never in a downloaded file.

  Editing model: double-click a block to edit it in place (Valider/Annuler in the corner); for tables, double-click a *cell* rather than a row. Editing always shows raw Markdown/LaTeX source (no rich-text toggle). Confirming an edit that actually changed the text triggers `captureCorrection`, which snapshots the block, bbox, and image source and opens `CorrectionModal`; confirming the modal crops the image and posts to `/corrections`. A bbox drag alone (no text change) never triggers a correction capture, since there's no before/after text pair to record.

  Two behaviors worth knowing before touching any of this:
  - **Uncertain-content highlighting** (`utils/markdownHighlight.ts`): `==...==` markers from the backend are rendered as `<mark class="ocr-uncertain">` via the `remark-highlight-mark` plugin (a micromark-level syntax extension, registered alongside `remark-gfm`/`remark-math`), *not* a post-parse text search/replace — a regex approach breaks as soon as the marked span straddles a `$...$` formula, because `remark-math` has already split that text into separate AST nodes by the time a text-only regex would run. That still leaves one case `remark-highlight-mark` structurally cannot handle: `==...==` placed *inside* a `$...$`/`$$...$$` span (e.g. `$f(==5==) = ==12==$`) — `remark-math` treats everything between the dollar signs as opaque LaTeX source, so the `==` markers are never tokenized and get sent to KaTeX literally, rendering as two stray `=` signs. `preprocessMathHighlights` (with its `highlightUncertainInMathSource` helper) works around this by pre-processing the raw Markdown *before* it reaches `ReactMarkdown`, converting `==...==` found inside math delimiters into `\colorbox{#FDE3B8}{...}` — a KaTeX-native command — so the highlight renders inside the formula itself instead of leaking as literal text. Outside math spans, `remark-highlight-mark`/`<mark>` still handles it as before. Only applied to the read-only rendered Markdown, never to `editDraft`/`cellDraft` — editing must always show the true raw source.
  - **Table rendering** (`utils/tableMarkdown.ts` + `components/result/TableRow.tsx`): since the backend emits one block per table row, `groupBlocksForRender` groups consecutive table-row blocks into one visual `<table>` (header rendered once from the first row's own header line, via `parseTableRowCells`). Each row is an independent `TableDataRow` (`React.memo`, keyed on `block.id`), and each non-confidence cell is an independent `TableDataCell` (`React.memo`, `useMemo` on that cell's own text value only) — **not** one shared `<ReactMarkdown>` call for the whole table. This granularity exists specifically so that selecting a row or editing one cell never re-parses/re-typesets KaTeX for *any* other cell or row: `TableDataCell` reads whether *it* is the one being edited from `EditingCellContext` (changes only on double-click start/stop, not per keystroke) rather than from a prop threaded down from a memoized ancestor, and the live-typed value flows through a separate `CellDraftContext` (changes every keystroke) consumed only by the one active `CellEditor` — so a keystroke in one cell never invalidates any other cell's memo. Row/cell click handlers reaching `ResultScreen.tsx` (`handleRowClick`, `onCellDoubleClick`, etc.) must stay `useCallback`-stable (backed by "mirror refs" — `editingCellRef`/`cellDraftRef`/`blocksRef` — for handlers that need the *current* value without invalidating their own memoization) or the whole per-row/per-cell memoization breaks silently. Row selection (`handleRowClick`) is also debounced 300ms and cancelled by a same-cell double-click (`rowClickTimerRef`), because dispatching `SELECT_BLOCK` synchronously on the first click of a double-click re-renders/highlights the row between the two clicks, which the browser then fails to recognize as a `dblclick`. The "Confiance" column (column 0, injected by the backend) is excluded from cell editing. The cell editor's `<input>` uses `[font:inherit] h-full block` and `size={1}` so it matches the KaTeX cell's font/height and doesn't widen the column with its default intrinsic width.
  - **Known limitation**: editing a cell/block containing a complex formula (fraction, exponent) shows the raw LaTeX source rather than the rendered text, causing a visible layout jump on entering/leaving edit mode. There's no rich-text/raw-code toggle for this — it's accepted as-is.
- `src/types/index.ts` — shared types mirroring the backend's Pydantic schemas (`TranscriptionBlock`/`Block`, `BoundingBox`, `TranscriptionResult`/`OCRResult`, PDF job start/status types) plus `ExportPage` (the per-page-source shape both export paths build from, see `exportPdf.tsx`/`exportExcel.ts` above). Correction request/response types (`SubmitCorrectionParams`, `CorrectionResponse`) live in `src/services/correctionsApi.ts` instead, not here. Keep these in sync manually when backend schemas change — there is no shared/generated type layer between the two projects.

Styling is Tailwind v4 via `@tailwindcss/vite` (no `tailwind.config.js` — v4 uses CSS-based config, see `src/index.css`/`App.css`). `src/index.css` also has manual `table`/`th`/`td` styling for `.markdown-content`, since Tailwind's preflight strips native table borders/spacing. Math rendering uses KaTeX exclusively; all icons in the app are inline hand-written SVGs (no icon library dependency).

## Frontend ↔ backend API key (implemented 2026-08-13)

The backend now requires a shared secret on every request to `/transcribe*`, `/corrections`, and `/export/pdf` (not on `/` or `/health`): header `X-API-Key`, checked by `app/security.py`'s `verify_api_key` FastAPI dependency against `APP_API_KEY` (`app/config.py`, distinct from `ANTHROPIC_API_KEY`). The frontend sends it automatically from `VITE_APP_API_KEY` via `src/services/apiClient.ts`'s `fetchApi`. Both `.env`/`.env.example` pairs (backend and `hakili-ocr/`) were updated accordingly; `hakili-ocr/src/vite-env.d.ts` types the new `import.meta.env.VITE_*` keys.

**Known limitation, by design, not a bug to fix**: a `VITE_*` variable is baked into the JS bundle at build time and is therefore visible to anyone who inspects the shipped frontend (view-source, Network tab) — it is *not* a secret once deployed. It blocks anonymous/automated direct hits on the bare API URL, but is not real user authentication and does not by itself prevent a motivated visitor from extracting the key and calling the API directly (see rate-limiting gap below).

## Docker / deployment (implemented 2026-08-20)

The app is dockerized: `ocr-math-api/Dockerfile`, `hakili-ocr/Dockerfile`, and root `docker-compose.yml` running both services together (see "Docker" under Commands above for the exact build/run commands). Both Dockerfiles already build in the practices flagged as "decide up front" during the pre-dockerizing security review below: non-root `appuser` in both images, multi-stage builds (build tools/npm cache never ship in the final image), pinned base image tags (`python:3.12.7-slim-bookworm`, `node:24.14-slim` for the builder stages, `nginx:1.27-alpine` for the frontend runtime — not floating, though not pinned to a digest), and `data/` is a named Docker volume (`backend_data`) mounted at `/app/data`, never copied into the image.

**Decided**: `VITE_API_BASE_URL`/`VITE_APP_API_KEY` are baked in at `docker compose build` time (passed as build args from the root `.env`), not injected at container startup — so a single built frontend image is tied to one backend URL/key pair. Rebuilding the frontend image is required to point it at a different backend (e.g. switching environments), rather than just restarting the container with different env vars. Accepted for the current single-environment deployment; would need revisiting (e.g. an entrypoint script substituting a placeholder in the built JS/HTML) if multiple environments from one image ever become a requirement.

### Local dev troubleshooting: "backend unreachable via `localhost`" on Windows (observed 2026-08-21)

On a Windows host running Docker Desktop with the WSL2 backend, `http://localhost:<port>` can silently stop reaching the backend container — the browser/`curl` request hangs or times out, while the container itself is healthy and logs zero incoming traffic. Cause: Windows resolves `localhost` to `::1` (IPv6) first, and a **stale `wslrelay.exe` process** (leftover from an earlier Docker session on the same port) can end up bound specifically to `[::1]:<port>`, shadowing the real `com.docker.backend.exe` proxy that's correctly bound to `0.0.0.0:<port>`/`[::]:<port>`. `http://127.0.0.1:<port>` still works fine in this state (IPv4 isn't affected) — that split (127.0.0.1 works, localhost doesn't) is the tell.

Diagnose with `netstat -ano | grep <port>` (look for **two different PIDs** listening on the same port — one `com.docker.backend.exe`, one `wslrelay.exe`) and confirm the culprit's identity with `tasklist //FI "PID eq <pid>"`. Fix: `taskkill //F //PID <wslrelay-pid>` (kills just the stale relay, safe — Docker's own proxy re-claims the port cleanly) or, if that's not enough, `wsl --shutdown` + restart Docker Desktop (more disruptive — drops all WSL distros, not just this project's containers).

## Security review — before dockerizing / deploying (2026-08-13; Docker-specific items resolved 2026-08-20)

Audit done in preparation for containerizing the app. Ordered by severity — items resolved by the Docker setup above are struck through; the rest are still open.

**Critical:**
1. ~~**No cap on PDF page count**~~ **done** — `convert_pdf_to_images` (`utils/image_utils.py`) now takes `max_pages` and rejects (`ValueError` → 400) before rasterizing any page if the PDF exceeds `MAX_PDF_PAGES` (default 600). PDF size limit is now also a dedicated `MAX_PDF_SIZE_MB` (default 500) rather than derived from the image limit.
2. ~~**No `.dockerignore`**~~ **done** — both `ocr-math-api/.dockerignore` and `hakili-ocr/.dockerignore` exist and exclude `.env`/`.env.*`, `data/` (backend) and `node_modules/`/`dist/`/`.env*` (frontend), so a `COPY . .`/`COPY app ./app` doesn't bake secrets or generated output into image layers.

**Important — still open:**
3. **No rate limiting on any endpoint** — combined with the `VITE_APP_API_KEY` limitation above, nothing stops a client who has extracted the key from the shipped frontend bundle from hammering `/transcribe` — direct, uncapped cost exposure via the Anthropic API. Needs a per-key/per-IP rate limit (e.g. `slowapi`, or handled at the reverse-proxy/CDN level).
4. **Generic exception handlers leak internal error text to the client** — e.g. `detail=f"Erreur inattendue : {exc}"` in `transcription.py`/`corrections.py` returns the raw Python exception message in the HTTP response instead of logging it server-side only and returning a generic message.
5. **Non-constant-time API key comparison** — `provided_key != settings.APP_API_KEY` in `app/security.py` is still a theoretical timing-attack surface. Fix: `secrets.compare_digest(...)` instead of `!=`, cheap to apply.
6. **Dependencies unpinned, never audited** — `requirements.txt` still uses `>=` floors, not exact pins; worth running `pip-audit` once before freezing a Docker image, and pinning the base image by digest (not just tag) for full reproducibility.

**Minor, not urgent:**
7. `allow_credentials=True` in the CORS middleware isn't needed (auth is header-based, not cookie-based) — harmless as-is but superfluous.
8. No security headers (CSP, etc.) — normally the responsibility of whatever sits in front of the app (nginx/Vercel/Railway); `hakili-ocr/nginx.conf` doesn't set any yet.
